# 雷达自然断流调查

调查日期：2026-08-31。用户要求先查原因，不改颜色。本轮未修改或部署运行源码、二进制、参数或 Foxglove 布局，未主动发送启停/复位命令。原驱动自己的恢复机制仍在运行。

## 结论边界

已确认雷达数据源停流，不只是 Foxglove 绘制停顿。存在明显的高温/测温异常线索，但不能据现有记录确诊“过热保护”，也不能排除传感器硬件、供电或固件问题。此前 210 秒正常窗口不代表后续长期稳定。

## 实际证据

- 原始生产日志：`evidence/radar-thermal-investigation-20260831.log`，本轮从板端只读下载。不是合成测试数据。
- 日志中有 8 个新的断流周期（`attempt=1`），10 条设备 trace `sensor fail 1 to reboot`。停流时 UDP 包数和完整帧数停止增长，发布队列为空；历史 `expired=9/put_errors=1/put_max_ms=2471` 未增加，来自此前发送阻断测试。
- 首次停流前，传感器读数从 63.79°C（frame 45300）跳到 84.58°C（frame 45350），随后为 86.72、86.99、87.12、87.26、87.39、87.47°C（frame 45650）。到 frame 45674 后停止收到完整帧。点云日志是抽样记录，不能称 87.47°C 为停流瞬间的精确温度。
- 温度换算有厂家依据：官方 Python 图像示例以 `frame.temperature / 100` 显示摄氏温度。源码：<https://github.com/XT-Toffuture/xtsdk_py/blob/main/sdk_example/sdk_example_img.py>，`onCallbackImage` 和 `TimerThreadFunc`。本地 SDK `cmdstructs.h` 标明 temperature[0] 为 sensor、[1] 为灯板，不能将其当作外壳温度。
- 后续断流前也记录到 62.11、63.58、66.39、58.89、58.63°C。两个极短恢复段没有新的温度日志，不能复用上个周期读数冒充实时值。逐次对照见 `evidence/radar-thermal-outages-20260831.json`，保留温度所在帧与停流帧的差距。
- 1049 条抽样温度日志的帧状态全部为 3（连续输出），未在这些日志中见到 7/8/9 高温状态。这不等于故障时没有报警：没有帧时不能从帧尾取得新状态。
- 传感器读数出现约 5 秒内跳升 20.79°C、另一周期 80.03°C 又回落到 66.39°C 的现象。可能是实际温升，也可能是测温/内部读数异常，不能仅由数值断言外壳实际到达该温度。
- 板端 xt_radar PID 14084、xt_camera PID 11631 未退出；本轮板端 SoC 温度读到 48.528°C，这是 RK3562 温度，不是雷达温度。eth1 carrier=1、100Mbps；接口 rx_errors/rx_dropped 为 0。内核最近链路变化在 uptime 115244 秒，本轮 uptime 已超过 121400 秒，不能把早前换交换机事件当作当前掉线。

## 尚缺的关键证据

本轮短时只读采样结果：`evidence/radar-thermal-passive-60s-20260831.json` 共 60 次状态采样，首末样本间新增接收 299 帧，seq 同样增加 299，按首末实际采样间隔约 5.0055Hz；最大采样数据年龄 202.2ms，stale 与时间戳回退计数均未增加。此为每秒轮询状态，不是逐帧间隔验收。同期 45 秒板端证据 `evidence/radar-thermal-network-45s-20260831.txt` 中 UDP InErrors/RcvbufErrors 保持历史 26238、不增加，TCP 重传保持 3394、不增加，eth1 rx_errors/rx_dropped=0，雷达 sensor 末次 56.30°C，板卡 SoC 47.903°C，两个进程 PID 未变。说明观察窗口暂时恢复，不证明故障已根治。

1. 厂家手册第 25 页的状态码：0x07 高温告警、0x08 高温降频、0x09 高温停流；0x04/05 为 CSI/I2C，0x10/11 为供电电压/电流异常。现有 `decode_radar_response` 只返回 command status，漏记 TCP 回包里的 device state；日志 `status=0` 不能当作“无温度报警”。
2. `sensor fail 1 to reboot` 是固件 trace 文本，文本中的 1 不能擅自解释为某个温度/电源状态码；`41 00 00 00 00 00` 也没有已确认的故障位定义。
3. 驱动在 >3 秒无帧时开始 stop/start，每三次 TCP 接通但测量未恢复时发送 cmd13 reset，并只等待 4 秒。日志又显示设备自身初始化过程，因此后续 16-48 秒级恢复过程可能被重复命令拉长。不能将全部重置都称作雷达自主重启，也不能因此反推最初停流由驱动 reset 引发：最初 UDP 先停，恢复命令在后。
4. 本轮没有抓到故障瞬间的 TCP device state 原包。板端无现成 tcpdump/Python/gcc；为了保持现状，未安装抓包软件、启动构建容器或部署诊断程序。
5. 未测实际供电电压纹波/压降、未测外壳温度、未进行单变量散热对照。不能宣布供电正常或热故障已排除。

## 最小验证路径

- 优先在保持电源、线缆和采集参数不变的前提下，用外部风扇改善散热，对照传感器温度和断流次数；不降采集配置，不屏蔽温度保护。不用手触摸判断温度。
- 厂家手册第 3 页建议散热措施使外壳不超过 60°C；这不是内部 sensor 的已确认停机阈值。手册第 4 页热保护段还混写 M120 型号，不能据此编造本块 M60 的具体阈值。
- 如果改善散热后仍复现，应补采设备状态原包，并用符合该设备铭牌/厂家要求的电源做供电对照。换电源/接头前断电，不进行带电插拔试验。
- 状态感知恢复是后续代码改进项：保留 INIT/过热状态和最后故障，避免在保护或初始化过程中频繁启停/复位。本次未实施，不把它报告成已修复。

参考原始手册：`docs/reference/XT-M60-datasheet.pdf`；本地 SDK 状态定义：`vendor/xtsdk/xtsdk/xtsdk.h`。

## 2026-09-01异常点云与反复重启

后续现场状态否定了“重新上电后已稳定”的外推。板端日志出现反复停流、`sensor fail 1 to reboot`、芯片初始化、短暂恢复的循环。只读归档`evidence/radar-weird-full-20260901.log`为4373745字节；其中7303个点云日志温度样本，sensor范围-293.70至310.95°C，3204个低于-40°C或高于125°C；frame devstate记录全部3。累计735条sensor fail trace、772个attempt=1停流起点和772次valid frames resumed。这些次数是同一生产日志累计，不等于物理上电次数。

`evidence/current-weird-pointcloud-range-20260901.json`独立订阅50帧、139453点，无接收队列丢弃。逐帧点数820-4375；总体距离min0.001m、P50 8.697m、P95 36.831m、P99 48.485m、max50.000m，强度P50 229、P95/P99/max 255。M60手册标称室内0.3-20m，当前0-50m数据及强度饱和不应解释为雷达突然具备50m可靠量程。协议结构可解析、Zenoh/Foxglove可传输，和传感器测量可信是两个问题。

PC `gateway.py`对点云仅检查Array1/header/scaler1000，并将xyz除以1000打包，全部收到点按原顺序传给Foxglove；没有20m裁剪或点数抽稀。因此怪形状主要来自当前源数据。Foxglove通道固定frame_id=lidar、单位姿态，没有IMU或TF姿态补偿：转动雷达会改变环境在lidar坐标系中的表示。若源停流，Foxglove通常保留最近一条PointCloud；遮挡后图形不变可能只是旧帧仍显示，应结合`/api/status`的age/healthy判断。完全遮挡时若仍有新帧，近于0.3m盲区的手也可能产生无效/近距反射，但不能解释错误温度和固件重启。

静电没有直接证据。手放在密封光学窗前不是通常的ESD电流路径；触碰裸露插针、未接地金属、线缆屏蔽或带电插拔才会提高可能性。当前优先级应为：雷达内部硬件/测温或数据链路、供电/接地/EMI、固件状态，其次才是未证实的单次静电事件。外部散热风扇若与雷达共用供电，应检查启动电流、纹波和地回路；是否共用待用户确认。本轮不降低量程、不滤掉怪点、不改协议数据掩盖问题。
