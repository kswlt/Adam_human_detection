# Zenoh QoS 板端验收报告（2026-09-03）

本报告对应《空间相机通信协议 V1.0》第 10 节。范围仅为 Zenoh QoS 显式配置及真实板端回归；未修改传感器算法、Protobuf wire format、现有有界队列或第三方源码。

## 1. zenoh-pico 版本/commit

- 项目实际使用 `vendor/zenoh-pico/version.txt`：`1.10.0`。
- 该目录不是独立 Git 仓库且没有上游 commit 元数据，不能伪造 commit。可复核快照 SHA-256：`version.txt=e91dee3b...fe30c1`、`api/types.h=0003e1da...95116f`、`src/api/api.c=3cccb9c7...f4eccf`。
- 未升级或修改 `vendor/zenoh-pico`。构建启用其已有 `Z_FEATURE_UNSTABLE_API`，因为 publisher reliability 字段受该宏控制；保留 `FRAG_MAX_SIZE=300000`。

## 2. 使用的 QoS API 和字段

- `z_publisher_options_default()` 初始化 `z_publisher_options_t`。
- 显式设置 `congestion_control`、`priority`、`reliability` 后传给 `z_declare_publisher()`。
- 订阅端 C 探针使用 `z_sample_congestion_control()`、`z_sample_priority()`、`z_sample_reliability()` 检查真实样本。
- `z_queryable_options_t` 没有 QoS 字段。`z_query_reply_options_t` 的 congestion/priority 已被 1.10.0 标记为 ignored，reply 继承 query；也没有 reply reliability 字段。

## 3. pointcloud 最终 QoS

正式主题 `active/LX2601F10001/pointcloud` 实测 20/20：`Drop(0) + Data(5) + BestEffort(1)`，通过。`pointcloud_preview` 保留 `Drop + Data + BestEffort`，未改变结构。

## 4. image 最终 QoS

正式主题 `active/LX2601F10001/image` 实测 20/20：`Drop(0) + Data(5) + BestEffort(1)`，通过。同一 publisher 同时覆盖 JPEG/H264，不按格式分叉 QoS。

## 5. imu 最终 QoS

publisher options 已局部设置为 `Drop(0) + RealTime(1) + BestEffort(1)`，启动日志来自实际 options。按任务要求未修改或重新验收 IMU 业务数据，因此只判代码/构造通过，不声称真实 IMU 样本通过。

## 6. config_file 最终 QoS

`active/LX2601F10001/config_file` C 探针实测为 `Block(1) + Data(5) + Reliable(0)`；subscribe/get 均可解析 `FileMsgArray`，通过。

## 7. cmd 最终 QoS

请求端显式以 `Block + Data` 发起；1.10.0 内部将 query 与 reply transport 固定用 `Reliable + Block` 发送，reply 的 priority/congestion 继承请求。安全 setting 请求回复实测为 `Block + Data` 且 `Error.code=0`。最终线上语义为 `Block + Data + Reliable`，但板端 queryable/reply API 不能逐条显式设置这三个值，详见第 9 项。

## 8. Priority 枚举对应关系

| 协议文字 | zenoh-pico 1.10.0 | 实际值 | 处理 |
|---|---|---:|---|
| Data (5) | `Z_PRIORITY_DATA` | 5 | 数字和语义一致 |
| RealTime (6) | `Z_PRIORITY_REAL_TIME` | 1 | 按语义使用 1 |
| 协议中的 6 | `Z_PRIORITY_DATA_LOW` | 6 | 不误用为 RealTime |

## 9. API 不支持项及兼容处理

1. queryable 声明阶段没有 QoS 字段；reply congestion/priority 字段被明确忽略，reply reliability 字段不存在。最接近实现是要求请求端使用 `Block + Data`，并依赖 1.10.0 已确认的 reply `Reliable + Block` 发送路径。若必须由回复端独立指定全部 QoS，需要升级/修复库 API。
2. 1.10.0 的分片路径在 `src/transport/common/tx.c:466` 将 reliability 枚举先转成 bool，而该版本枚举是 `Reliable=0`、`BestEffort=1`，导致大消息线上值反转。对照实测：未补偿的大 JPEG 为 Reliable，小于 2 KB 的 preview 为 BestEffort。遵守“不修改 vendor”约束，应用层仅对必然分片的完整 image/pointcloud 使用反值补偿；启动日志同时打印 API 值、目标 wire 值和 workaround 名称。补偿后正式两主题 C 探针均为 BestEffort 20/20。
